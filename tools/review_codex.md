승우님, 가장 먼저 고칠 것은 **‘혼자 만든 사람’이라는 강조에 비해, ‘조직에서 시스템을 책임질 개발자’라는 근거가 부족한 점**입니다.

파일 읽기는 실행 환경 오류로 실패했습니다. 아래는 **이미지 1의 최신 카드와 이미지 2의 최신 패널 기준**이며, 소스·링크·수치의 실제 근거는 검증하지 못했습니다. 대안 문장 중 실적에 관한 내용은 확인된 사실만 적용해야 합니다.

1. **[포지셔닝] 배너의 ‘한 사람이 직접 합니다’**
   
   문제 → “기획·운영과 개발을 한 사람이 직접 합니다”는 역량보다 혼자 일한다는 방식을 전면에 내세웁니다.  
   왜 → SI 개발 리더에게는 요구사항 합의, 변경 관리, 인수인계도 중요합니다. 현재 문장은 협업 가능성보다 개인 의존도를 먼저 떠올리게 할 수 있습니다.  
   대안 → **“교육 운영의 요구사항을 분석하고, 업무 시스템을 개발·운영합니다.”** 아래에는 “공공 AI 교육 기획·운영 담당 · 사내 서비스 4개 개발·운영”처럼 직무와 개발 실적을 구분하세요.

2. **[신뢰성] ‘4개 프로덕션’의 경계와 개발 경력 기간**
   
   문제 → 카드 여섯 개에 운영 서비스·개인 프로젝트·배포 준비작이 섞여 있고, 개발 업무를 수행한 전체 기간은 바로 보이지 않습니다.  
   왜 → 경력직 검토에서는 무엇을 만들었는지와 함께, 언제부터 얼마나 오래 책임졌는지를 확인합니다. 출시일만으로 유지보수 경험을 판단하기 어렵습니다.  
   대안 → 소개에 **“기획·운영: YYYY.MM–현재 / 개발 업무 병행: YYYY.MM–현재”**를 넣고, 프로젝트를 “업무 서비스 4개”와 “개인 프로젝트”로 나누세요. 각 서비스에 개발 기간과 운영 기간을 따로 적으세요.

3. **[기술 근거] 화면과 스택에 비해 설계 판단이 부족함**
   
   문제 → 카드 대부분이 기능 목록과 “요구분석·설계·개발·운영”으로 끝납니다.  
   왜 → 같은 문구를 반복해도 개발 깊이는 드러나지 않습니다. 면접관은 권한, 데이터 정합성, 장애 대응에서 어떤 선택을 했는지 물을 가능성이 큽니다.  
   대안 → EMS·CBT 두 개에 **“업무 제약 → 설계 결정 → 검증 결과”** 사례 링크를 붙이세요. 실제 구현한 범위에서 권한 분리, 시험 제출 처리, 데이터 이관 등의 결정 하나씩을 구체적으로 보여주세요.

4. **[숫자] 배너의 41·8,180·1,449·108**
   
   문제 → 운영 규모, 누적 인원, 동시 접속 수가 같은 종류의 성과처럼 배치되어 있습니다.  
   왜 → 지원 건수는 개발 성과와 다르고, “CBT 동시 108”은 실사용 기록인지 부하 테스트인지 불명확합니다. 이미지 1에는 “100명 검증”도 보여 설명이 필요합니다.  
   대안 → **“누적 지원 ○건 · 집계 기간 ○○”**, **“실시험 최대 동시 응시 ○명 · 측정 기준 ○○”**처럼 정의하세요. 실제 운영과 테스트 수치는 분리하고, 개발 전부터 누적된 데이터라면 이관 데이터임을 밝히세요.

5. **[역할 패널] ‘전 주기 담당’과 ‘전 단계 직접 수행’의 중복**
   
   문제 → 운영·개발 패널 모두 전 과정을 맡았다는 주장에 집중하며, “운영자 10명+”는 동료 사용자인지 관리 인원인지 모호합니다.  
   왜 → 담당 범위가 넓다는 주장만으로는 책임의 경계가 보이지 않습니다. 최신 이미지에서는 개발 패널의 기술 나열도 오른쪽으로 잘립니다.  
   대안 → 왼쪽은 **“선발·교육·인증평가 운영 / 현업 요구사항 정리·업무 절차 설계”**, 오른쪽은 **“업무 시스템 4개 개발·운영 / 웹·API·DB 구현 및 배포”**로 줄이세요. “운영 담당자 10명 이상이 사용”처럼 관계를 명시하고, 기술 목록은 Stack으로 옮기세요.

6. **[How I work 1·2] 선언이 많고 작업 산출물이 없음**
   
   문제 → “한 사이클을 직접 수행한다”, “코드보다 문서 먼저”, “모든 저장소에…”는 범위가 크고 단정적입니다.  
   왜 → 첫 줄은 역할 패널과 중복됩니다. 두 번째는 문서를 실제 의사결정과 유지보수에 어떻게 쓰는지 설명하지 못하며, “모든”은 검증 부담만 늘립니다.  
   대안 → ① **“현업 요구사항을 정리하고, 구현 후 운영 담당자와 업무 흐름을 검증합니다.”** ② **“주요 설계 결정과 운영 절차를 문서화하고 변경 시 갱신합니다.”** 각각 실제 문서나 검증 사례로 연결하세요.

7. **[How I work 3·4] ‘설계를 버린다’와 핵심 통제의 미완성 인상**
   
   문제 → “안 맞으면 설계를 버린다”는 과격하고, “지금 보강 중: 테스트 자동화, DB 접근 권한(RLS)”은 운영 서비스의 현재 상태를 불안하게 만듭니다.  
   왜 → SI 맥락에서는 변경 영향과 이행 계획이 중요합니다. RLS 보강이라는 표현만으로는 현재 접근 통제가 있는지 없는지 알 수 없습니다.  
   대안 → ③ **“실데이터로 가설을 검증하고, 결과에 따라 기능 범위와 설계를 조정합니다.”** ④는 **“운영 중 확인된 오류를 회귀 테스트에 반영합니다”**처럼 실제 수행 중인 행동으로 쓰세요. 미완료 과제는 프로젝트별 현재 통제 방식·남은 작업과 함께 명시하세요.

8. **[카드 카피] 긴 기능 나열과 검증하기 어려운 효과**
   
   문제 → EMS의 여덟 단계 화살표, CBT의 기능 목록 뒤에 “반복된 문제 4개를 설계에서 제거”가 이어집니다.  
   왜 → 작은 카드에서 읽기 어렵고, “제거”는 문제가 재발하지 않는다는 강한 주장입니다. 정작 어떤 문제가 어떻게 줄었는지는 없습니다.  
   대안 → EMS는 **“모집부터 수료·결과보고까지 교육 운영 데이터를 한 시스템에서 관리.”** CBT는 **“문항 관리·시험 진행·감독·결과 내보내기를 통합한 사내 CBT.”**로 줄이세요. 해결한 문제는 상세 문서에서 이전 절차와 변경 결과로 설명하세요.

9. **[카드 지표] 11,000+·4.0/5·1.1%·PASS의 의미**
   
   문제 → 데이터 규모, 평가 점수, 실패 가설의 수치, 에이전트 판정이 카드 하단의 대표 성과 자리를 각각 차지합니다.  
   왜 → 11,000건은 서비스 이용 성과가 아니며, 4.0/5는 평가자·표본·기준이 없으면 의미가 약합니다. 에이전트의 PASS도 코드의 정확성을 보증하지 않습니다.  
   대안 → **“공고 ○건 수집·색인”**, **“평가 ○건 평균 4.0/5 · 평가 방식 링크”**로 정의하세요. 1.1%는 분모·매칭 기준을 사례 문서에 밝히고, PASS는 **“자동 검토·수정 루프 구현”**으로 바꾸되 테스트 통과와 구분하세요.

10. **[구조] 여섯 프로젝트를 같은 비중으로 제시**
    
    문제 → EMS·CBT와 개인용 Agent Pipeline·배포 준비 중인 AI쏙이 동일한 크기로 배치됩니다.  
    왜 → 실운영 경험이라는 핵심 근거가 희석되고, 미완성 작업까지 검토해야 소개의 중심을 파악할 수 있습니다. “5 pinned · 1 next”도 채용 판단에 도움이 적습니다.  
    대안 → **소개·경력 요약 → 대표 사례 EMS·CBT → 기타 업무 서비스 → 일하는 방식 → 기술 → 개인 프로젝트·연락처** 순으로 구성하세요. 개인 프로젝트는 텍스트 링크로 축소하고, 준비작은 공개 가능한 결과가 생긴 뒤 올리세요.

11. **[기술·라벨] 기술 이름은 많고 사용 수준은 없음**
    
    문제 → React 19, Next.js 16, GraphRAG, Multi-agent orchestration 등이 동일한 배지로 제시되고, `production`, `python`, `nolab`, `next`도 서로 다른 기준의 라벨입니다.  
    왜 → 실제 운영 기술과 실험 기술을 구별하기 어렵습니다. 특히 AI 용어가 많으면 기본적인 백엔드 설계보다 도구 사용을 강조한 인상이 생길 수 있습니다.  
    대안 → Stack을 **“업무 서비스에서 사용” / “개인 프로젝트에서 실험”**으로 구분하고 프로젝트에 연결하세요. 카드 상태는 **“운영 중 / 개발 중”**으로 통일하고, 언어·도메인·소속은 별도 메타데이터로 분리하세요.

12. **[가독성] SVG 축소와 작은 화면 캡처**
    
    문제 → 작은 메타데이터와 카드 속 화면의 글씨가 전체 렌더링에서 거의 읽히지 않습니다. 개발 패널은 최신 이미지에서도 잘립니다.  
    왜 → 이미지 안의 텍스트는 표시 폭이 줄면 함께 작아집니다. GitHub 본문 폭에서 읽히지 않으면 정보가 있어도 검토에 쓰이지 않습니다.  
    대안 → **900px 원본을 720px로 표시하는 조건**이라면 본문 20px→16px, 보조 글자 16px→12.8px를 기준으로 잡으세요. 카드 제목은 표시 기준 18–20px, 핵심 수치는 20–24px로 하고, 화면은 전체 대시보드 대신 핵심 부분을 확대하세요. 긴 설명은 마크다운 본문에 두세요.

13. **[시각 위계] 모든 섹션이 무거운 다크 패널**
    
    문제 → 역할·섹션 제목·카드·How I work·Stack·Where가 모두 짙은 배경과 격자를 사용합니다.  
    왜 → 같은 시각적 무게가 반복되어 중요한 프로젝트가 두드러지지 않습니다. 연락처와 기술 목록도 대표 실적만큼 공간을 차지합니다.  
    대안 → 다크 배경은 **역할 요약과 프로젝트 썸네일**에 집중하고 나머지는 기본 마크다운으로 바꾸세요. 목표 표시 크기 기준 섹션 간격 24–32px, 이미지 내부 여백 24–28px, 카드 모서리 12–16px로 통일하고 격자는 삭제하거나 불투명도 2–3%로 낮추세요.

14. **[브랜드 일관성] 색상 과다와 이미지 중심의 정보 전달**
    
    문제 → 초록·파랑·노랑·분홍이 프로젝트·기술·상태에 섞여 쓰이고, 주요 문장이 이미지 안에 있습니다.  
    왜 → 색의 의미를 학습하기 어렵고, 문구 검색·복사·이미지 미표시 상황에서도 내용 접근이 약해집니다. 실제로 첨부 자료에서도 패널 버전이 다르게 보입니다.  
    대안 → 강조색은 청록 하나, 상태 표시용 보조색 하나로 제한하세요. 이름·직무·성과·연락처는 마크다운 텍스트로 유지하고 SVG는 시각 보조로 쓰세요. 이미지에는 요약 대체 텍스트를 넣고, 갱신 시 파일명에 버전이나 해시를 반영하세요.
